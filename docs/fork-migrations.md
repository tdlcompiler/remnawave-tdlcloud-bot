# Миграции форка и upstream

Собственные ревизии называйте `tdl_<уникальное_имя>`, не занимайте числовые ID upstream. После слияния запускайте `uv run --frozen pytest tests/database/test_migration_chain.py tests/database/test_0141_collision.py tests/database/test_0142_transition.py -q`. CI также содержит тесты цепочки. Если upstream и форк независимо добавили миграции после общего предка, используйте merge-ревизию с двумя разными родителями и проверьте миграции на копии базы; upstream ID и связи не переименовывайте.

## Переход старой 0142

В одной версии форка уже была развёрнута ревизия `0142`; теперь это `tdl_renewal_01`. При запуске Alembic мост в `env.py` транзакционно проверяет поля email, таблицу и первичный ключ продлений, после чего меняет только отметку Alembic. При неполной схеме запуск останавливается и версия не переписывается. Данные не удаляются. Для PostgreSQL на время проверки блокируется `alembic_version`.

**Установите эту переходную версию на все существующие базы до слияния upstream, в котором появится его собственная 0142.** Когда в графе уже есть upstream 0142, старый и новый ID неоднозначны, поэтому мост намеренно не переписывает его. Нельзя пропускать переходную версию при обновлении старой базы напрямую на будущий upstream с 0142: тогда потребуется ручная диагностика схемы и истории. Сохраняйте резервную копию перед обновлением. Команды Alembic онлайн через стандартный `env.py` также используют мост; offline SQL-режим мост не выполняет.
