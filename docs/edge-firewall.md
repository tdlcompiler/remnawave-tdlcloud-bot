# Блокировка торрент-IP на фронтах через nginx :443

Бот хранит активные блокировки в SQLite и каждые 30 секунд отправляет каждому фронту IP и оставшийся срок. После перезапуска бота состояние берётся из файла; после перезапуска фронта правила восстанавливаются при следующей синхронизации. Повторная доставка не продлевает исходный срок. Это отдельная блокировка IP на фронте; уведомления пользователя работают как прежде.

## 1. Установить агент на фронты

Агент и Docker Compose вынесены в отдельный комплект `tdlcloud-firewall-agent`. Скопируйте его на каждый фронт и следуйте его `README.md`: создайте `.env` с уникальным токеном, настройте сертификат и запустите контейнер. Используйте отдельное SNI-имя, например `edge-fw.example.com`, присутствующее в сертификате. При обновлении сертификата перезапустите контейнер.

Контейнер слушает только `127.0.0.1:2053` и принимает PROXY v1 от nginx перед TLS. Для управления nftables используется сеть хоста и `CAP_NET_ADMIN`.

## 2. Изменить nginx на каждом фронте

В присланном конфиге уже есть `stream`, `ssl_preread on` и `proxy_protocol on`. В существующий `map $ssl_preread_server_name $backend` добавьте строку до `default`:

```nginx
edge-fw.example.com  127.0.0.1:2053;
```

Новый `listen 443` или отдельный HTTP location не нужны. Существующий `proxy_protocol on` должен оставаться включённым: агент ожидает этот заголовок. Не включайте завершение TLS на nginx для этого маршрута: сертификат предъявляет агент.

```sh
nginx -t && systemctl reload nginx
```

Убедитесь, что имя не пересекается с существующими маршрутами. Проверьте внешний TLS с машины бота, подставив IP конкретного фронта:

```sh
openssl s_client -connect FRONT_IP:443 -servername edge-fw.example.com -verify_hostname edge-fw.example.com -verify_return_error </dev/null
```

## 3. Настроить бота

В `.env` бота добавьте одну строку JSON (IP и токены заменить):

```dotenv
EDGE_FIREWALL_ENABLED=true
EDGE_FIREWALL_NODES='[{"host":"FRONT_1_IP","server_name":"edge-fw.example.com","token":"ТОКЕН_ФРОНТА_1"},{"host":"FRONT_2_IP","server_name":"edge-fw.example.com","token":"ТОКЕН_ФРОНТА_2"}]'
EDGE_FIREWALL_STATE_FILE=/app/data/edge_firewall.sqlite3
EDGE_FIREWALL_SYNC_SECONDS=30
```

Также включите и настройте подписанный вебхук Remnawave (`REMNAWAVE_WEBHOOK_ENABLED`, `REMNAWAVE_WEBHOOK_SECRET`, URL и событие `torrent_blocker.report`). Пример этих настроек есть в `.env.example`. Требуется доступ контейнера бота к обоим фронтам на TCP 443. При использовании частного CA укажите `EDGE_FIREWALL_CA_FILE` как путь **внутри контейнера** и примонтируйте файл. Настройки старого одиночного фронта поддерживаются, когда `EDGE_FIREWALL_NODES` пуст.

Пересоберите и перезапустите бот обычным для проекта способом, например `docker compose up -d --build bot`. Каталог `./data` в штатном compose примонтирован в `/app/data`: сохраняйте его при переносе и обновлении. Не запускайте несколько независимых экземпляров бота с разными локальными файлами состояния.

## 4. Проверить работу

Проведите тест на собственном тестовом IP, к которому не привязан доступ администратора. Убедитесь в реальном вебхуке: `data.report.actionReport.blocked` равно `true`, `ip` содержит клиентский IP, а `blockDuration` — секунды, от 1 до 604800. Если формат или единицы отличаются, интеграцию нужно адаптировать. Проверяйте, что IP, который видит nginx на обоих фронтах, совпадает с IP в отчёте.

После события проверьте логи бота и обоих агентов, а на каждом фронте:

```sh
nft list table inet edge_firewall
docker compose logs --tail=100 firewall-agent
```

Проверьте IPv4/IPv6 по необходимости, реальный запрет соединения и автоматическое снятие по истечении срока. Затем перезапустите один фронт или агент и проверьте восстановление активной блокировки. Отключите фронт на время события, включите до истечения срока и проверьте повторную доставку. Обновление правил происходит не мгновенно после восстановления, а в течение интервала синхронизации плюс время запросов.

Агент создаёт собственную таблицу nftables с цепочкой `input` и блокирует весь входящий трафик с IP, включая SSH, а не только VPN. Общий NAT может затронуть других пользователей. В зависимости от конфигурации Docker и маршрутизации часть трафика может проходить через `forward`; проверяйте фактический путь пакетов. При конфликте с другими средствами управления nftables или при очистке таблиц сторонним сервисом требуется отдельная настройка. Потеря файла состояния бота уничтожает очередь и активные блокировки для восстановления. Повтор вебхука до записи зависит от поведения панели; при ошибке записи бот отвечает HTTP 503.
